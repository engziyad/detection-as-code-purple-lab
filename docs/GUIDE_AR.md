# الدليل الكامل: Detection-as-Code Purple Lab

## الفكرة باختصار

أغلب قواعد الكشف في مراكز العمليات الأمنية تُكتب مرة وتُلصق في الـ SIEM ولا أحد يتأكد أنها فعلاً تشتغل. هذا المشروع يعامل قواعد الكشف كأنها **برمجيات**: كل قاعدة مكتوبة ككود، ومعها اختبارات، وتُفحص تلقائياً مع كل تعديل، ومعها سكربت يحاكي الهجوم اللي تكشفه.

النتيجة: تقدر تقول بثقة "هذي القاعدة تكشف الهجوم الفلاني، وهذا الدليل".

## ليش هذا المشروع يميّزك

| الشائع في GitHub | مشروعك |
|---|---|
| ملخصات كورسات و write-ups | أدوات تشتغل فعلياً |
| قواعد Sigma بدون اختبار | 51 حالة اختبار تنفّذ تلقائياً |
| Red **أو** Blue | الاثنين مربوطين ببعض (Purple) |
| خريطة ATT&CK مرسومة يدوياً | خريطة تتولد من القواعد المختبرة فقط |
| لا أحد يذكر نقاط الضعف | كل قاعدة موثّق فيها كيف المهاجم يتجاوزها |

## مكونات المشروع

### 1. مجلد `detections/`
كل تقنية MITRE لها مجلد فيه:
- **`rule.yml`**: قاعدة الكشف بصيغة Sigma (المصدر الوحيد للحقيقة).
- **`tests/true_positive.jsonl`**: أحداث هجومية، لازم القاعدة تكشفها كلها.
- **`tests/true_negative.jsonl`**: أحداث سليمة تشبه الهجوم، لازم القاعدة ما تنبّه عليها أبداً.
- **`README.md`**: شرح القاعدة: السجلات المطلوبة، المنطق، طرق التجاوز، تقليل الإنذارات الكاذبة، وخطوات التحقيق لمحلل SOC.

### 2. محرك Sigma الخاص (`tools/sigma_engine.py`)
بنيته من الصفر عشان يقدر يشغّل القواعد على الأحداث **بدون أي SIEM**. يدعم الـ modifiers الأساسية (contains, startswith, endswith, re, all…) والشروط المركبة (and/or/not والأقواس و `1 of`). إذا القاعدة فيها صيغة غير مدعومة، يطلع خطأ واضح بدل ما يرجع False بصمت.

### 3. أداة التحويل (`tools/convert.py`)
تحوّل كل قاعدة إلى:
- **KQL** لـ Microsoft Sentinel / Defender
- **SPL** لـ Splunk

وتستخدم نفس منطق المحرك، يعني الاستعلام اللي ينزل في الـ SIEM هو نفس المنطق اللي نجح في الاختبار بالضبط. أسماء الحقول والجداول في ملف واحد `mappings.yml`، تعدّله وتنقل المشروع لأي بيئة.

### 4. أدوات الجودة
- **`validate.py`**: يتأكد من اكتمال بيانات كل قاعدة، صحة الـ UUID، وجود تاغات ATT&CK، صحة الشرط، وجود الاختبارات والتوثيق، وعدم وجود TODO.
- **`run_tests.py`**: يشغّل الاختبارات ويطلع تقرير ملوّن + JUnit + جدول في صفحة GitHub Actions.
- **`coverage.py`**: يولّد طبقة ATT&CK Navigator وجدول تغطية. القاعدة اللي اختباراتها فاشلة تاخذ نص الدرجة، عشان الخريطة ما تبالغ.
- **`new_detection.py`**: ينشئ مجلد قاعدة جديدة جاهز. والمميز أنه **يفشل في الفحص عمداً** لين تكمّل كل الـ TODO.

### 5. سكربت المحاكاة (`emulation/Invoke-PurpleEmulation.ps1`)
يحاكي كل تقنية بطريقة آمنة ويرجّع كل شي مثل ما كان. كل تشغيل يحط علامة مميزة (marker) ويسجّل الوقت بالـ UTC، عشان تبحث عنها في الـ SIEM وتقيس **سرعة الكشف**. المحاكاة الحساسة (تفريغ LSASS) ما تشتغل إلا بخيار إضافي صريح.

### 6. خط الـ CI (`.github/workflows/detection-ci.yml`)
مع كل push أو pull request:
1. فحص القواعد
2. اختبار المحرك نفسه
3. تشغيل كل قاعدة على أحداثها
4. توليد KQL و SPL
5. توليد التغطية
6. **فحص الانحراف**: إذا الملفات المولّدة في الريبو ما تطابق القواعد، يفشل البناء

## القواعد الثمان ونقطة القوة في كل وحدة

| التقنية | وش يميّز القاعدة |
|---|---|
| **T1003.001** تفريغ LSASS | تعتمد على صلاحيات الوصول (access mask) مو اسم الأداة، وما تستثني System32 بشكل أعمى لأن `rundll32 comsvcs.dll` منه |
| **T1059.001** PowerShell المشفّر | regex يكشف كل اختصارات `-EncodedCommand` (`-e`, `-ec`, `-enc`…) وحتى الشرطات اليونيكود، ويكشف النسخة المعاد تسميتها |
| **T1218.011** rundll32 | أربع أنماط إساءة، منها rundll32 بدون معاملات (الحاضنة الافتراضية لحقن Cobalt Strike) |
| **T1053.005** المهام المجدولة | ما ينبّه على كل مهمة، فقط اللي تشير لمسار مشبوه أو مفسّر سكربت أو إنشاء عن بعد كـ SYSTEM |
| **T1547.001** مفاتيح Run | لازم المفتاح **و** القيمة يكونون مشبوهين، مع استثناء OneDrive و Teams |
| **T1569.002** تثبيت خدمة (PsExec) | بصمات PsExec و Impacket psexec/smbexec |
| **T1070.001** مسح السجلات | wevtutil و PowerShell و .NET و WMIC |
| **T1558.003** Kerberoasting | تذاكر RC4 لحسابات المستخدمين + استعلام تجميعي للصيد |

## التشغيل

```bash
pip install -r requirements.txt
make ci
```

وبدون make:

```bash
python tools/validate.py
python -m unittest discover -s tests
python tools/run_tests.py
python tools/convert.py --all --out queries
python tools/coverage.py
```

## كيف تشرحه في مقابلة

**جملة الافتتاح (30 ثانية):**
> "بنيت pipeline لهندسة الكشف يعامل القواعد ككود. كل قاعدة Sigma معها اختبارات إيجابية وسلبية تنفَّذ تلقائياً في CI، وتتحول تلقائياً إلى KQL و SPL، ومعها سكربت محاكاة يولّد نفس التليمتري. والتغطية في ATT&CK تتولد فقط من القواعد اللي نجحت اختباراتها."

**أسئلة متوقعة وأجوبتها:**

- **ليش بنيت محرك خاص بدل pySigma؟**
  عشان أختبر القواعد بدون SIEM، وأفهم بالضبط كيف يتم التقييم. pySigma ممتاز للتحويل، لكن الهدف هنا تنفيذ القواعد كاختبارات.

- **كيف تمنع أن تعديل (tuning) يكسر القاعدة؟**
  أي إنذار كاذب يتحول أول شي إلى true-negative test، بعدين أضيف الفلتر. لو الفلتر كسر true-positive، الـ CI يرفض الدمج.

- **وش نقاط ضعف قاعدة LSASS؟**
  تكرار الـ handle من عملية ثانية، والـ direct syscalls. الحل الحقيقي Credential Guard و RunAsPPL، والقاعدة خط دفاع إضافي. (هذا الجواب يوضح أنك تفكر كمهاجم ومدافع مع بعض، وهذا جوهر Purple.)

- **كيف تقيس نجاح الـ Purple Team؟**
  نسبة التقنيات المغطاة والمُختبرة، متوسط زمن الكشف، ونسبة التقنيات اللي ما أنتجت تليمتري أصلاً.

## أفكار للتوسع (تخلي المشروع يكبر معك)

1. قواعد ترابط (correlation) لـ password spraying و Kerberoasting.
2. قواعد Linux عبر auditd.
3. backend ثالث: Elastic EQL.
4. تشغيل الاختبارات مباشرة من ملفات EVTX حقيقية من المختبر.
5. قواعد لهجمات الويب المتقدمة (من خبرة eWPTX)، وهذا بيكون المشروع الثاني المكمّل.

## تنبيهات مهمة

- **لا تضيف أي بيانات من جهة عملك**: لا سجلات، لا أسماء أنظمة، لا حالات حقيقية. كل الأحداث في المشروع اصطناعية.
- **لا تنسخ محتوى من مواد الكورسات** (Zero-Point, INE) حرفياً، لأن شروطهم تمنع النشر.
- سكربت المحاكاة **للمختبر فقط** على جهاز معزول تملكه.
